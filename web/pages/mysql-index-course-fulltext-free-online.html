Queries Supported by FULLTEXT Indexes

Word-based search across text columns when MySQL tokenization and ranking semantics fit. A similar-looking predicate may not use the same access path; operators, expressions, key order, and data type all matter.

Read Performance, Storage, and Write Costs

Parser settings, stopwords, token length, and language affect matches; indexing adds maintenance. Indexes reduce some search work but require storage and add maintenance to writes.

FULLTEXT Indexes Limitations and Common Mistakes

FULLTEXT is not a general substring index; engine/version support and parser rules matter.

Do not assume that an index being present means the optimizer chose it or that the query became selective.

How to Measure and Tune FULLTEXT Indexes

Check parser configuration and test representative language, token lengths, query mode, and relevance.

Compare representative plans and timings before and after, including concurrent writes and realistic data volumes.

FULLTEXT Indexes Questions

Will the database always use this index?

No. The optimizer weighs selectivity, estimated costs, statistics, cache state, and the amount of data returned.

What should I verify before production?

Confirm version support, query compatibility, write overhead, build/rollback procedures, and index behavior during backup and recovery.
